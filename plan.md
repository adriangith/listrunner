## ListRunner Build Specification

### First-store welcome (30 October 2026)

* Fresh installs start with every store disabled. Show a neutral ListRunner welcome with `Choose your first store`, a brief purpose statement, three steps (choose a store, add/import a list, shop through items), and a prominent `Choose a Store` action opening Manage Stores. No permission requests or store websites open automatically.
* Keep the welcome across relaunches and cancelled store selection until a store is enabled. After that, disabling all stores shows `No stores enabled`, `Enable a store to see its grocery list.` and `Manage Stores`, not first-time onboarding. Existing installs retain their enabled stores and use the returning-user empty state. Confirmed Reset Local Data clears welcome completion.
* Debug builds accept `--preview-store-welcome` to display the welcome for one launch without clearing or changing lists, logins or store preferences. Choose a Store opens ordinary management; backing out without enabling a store returns to the welcome. An explicit store-enable action exits the temporary preview.

### Simplified import-source setup (30 October 2026)

This approved flow follows the simplified **Import sources** OpenPencil page and supersedes older multi-source favourite/preview proposals, not the Paprika transaction or reminder-writeback rules below.

* Before a source is configured, the list action is `Import`. It opens `Set import source`, currently containing Paprika only. Choosing Paprika opens export instructions; backing out does not configure or import anything.
* `Use Paprika` is a confirmation button, not a toggle. It persists the single app-wide active source and returns directly to Your list. This setup action neither imports nor requests Reminders access. Existing installations with no source preference also get this one-time setup.
* The configured list action is `Import from Paprika` and performs the existing immediate import into the selected store list. There is no per-import source chooser, preview/selection stage or automatic store presentation.
* Settings → `Import source` displays the active source and allows reopening the same chooser/instructions. Confirmation there also returns to Your list. Instructions explicitly tell users to export from Paprika to Apple Reminders; only an explicit subsequent import requests full Reminders access when required.
* Source setup does not change grocery rows, quantities, statuses, order, reminder links, drafts or retailer sessions. Store switches/relaunches preserve the source. Unknown source values return to setup; confirmed Reset Local Data clears the source preference. Other list/session/diagnostic clears do not.
* Only Paprika is offered until another integration is implemented and verified. Do not imply that the other five source concepts already work. Existing all-or-nothing import, store-local source-ID deduplication, incomplete-reminder filtering and best-effort writeback rules remain unchanged.

### Approved multi-store expansion (21 October 2026)

This expansion promotes bundled support for Woolworths, multiple store-bound lists, remembered store selection, and per-store sessions from Later Scope. The original Coles-only MVP requirements below remain the regression baseline; where they refer to the single list/store or hard-code retailer wording, use the following rules for the expanded build:

* One active store list is shown at a time, with separate persistent Coles and Woolworths lists selected through a native Store picker on Your list. Show Store and item-row actions always target the selected list's retailer. Each list retains its own order, statuses, selected item, and last-active local date. Same-day resume applies only to the selected list and only when Pending items remain.
* Existing unversioned GroceryItem data migrates into the Coles list without changing UUIDs, names, quantities, search terms, statuses, or positions. Empty store-list records are created idempotently, and the existing selected-item preference is migrated to Coles. Failed storage open/migration/backfill uses local recovery; never replace a failed store automatically.
* Store definitions are bundled, versioned, data-only JSON. A typed registry supplies trusted store identities and maximum exact HTTPS host allowlists. Definitions select named bundled search, trusted-tile quantity, stable numeric product-link identity, and verified decrement strategies; they do not contain executable scripts. Invalid definitions disable automation while preserving known-safe browsing and manual status controls. Adding arbitrary custom websites or editing executable code in the app is not part of this expansion.
* Preserve the existing Coles login in its default persistent WebKit data store. Woolworths uses its own named persistent data store. Runtime host checks, bridge validation, interaction/document/operation generations, recovery, reset, and Undo are scoped to the owning store. Switching lists cancels outstanding interactions without changing either cart or item status.
* Woolworths supports configured search, manual status controls, and verified add detection using the numeric product-details stockcode plus a stable quantity increase in the product tile. Cart Undo remains disabled until its decrement/reversal controls pass a separate live safety check. The public search route is `https://www.woolworths.com.au/shop/search/products?searchTerm={query}` with a percent-encoded query. A search-results shell alone is not evidence that cart automation works.
* Explicit Move to Another Store transfers the selected row's identity and quantity to the destination list, appends it, and changes its status to Pending after confirmation. It never moves or removes products in retailer baskets. Existing destination rows are not implicitly merged by this action. Typed/pasted duplicate merging remains scoped to the destination list only. Clearing a list affects only that store; confirmed Reset Local Data affects all ListRunner lists and metadata but no retailer website data or Reminders.
* Settings lists each retailer with independent reset and diagnostic-clearing actions, plus Clear All Diagnostics. Retailer reset verifies only that retailer's local website data/cookies were removed and preserves other store sessions and all ListRunner lists. Do not infer or display signed-in account state from cookies or credentials. A server cart may return after sign-in.
* Paprika/EventKit integration targets the explicitly selected store list; reminder identity, deduplication and best-effort writeback respect that list ownership. Import requires explicit full Reminders access and never runs on launch.
* Release validation adds legacy-store migration, configuration contracts, URL encoding, exact host policy, per-store item/status/selection isolation, cross-store bridge/Undo rejection, cookie/reset isolation, and live Woolworths/manual-fallback tests. All original accessibility, persistence, privacy, failure-recovery, no-automatic-product-selection, and no-checkout constraints still apply.

### Implemented UI and flow decisions (23 October 2026)

These newer implementation decisions supersede conflicting presentation and interaction details in the original Coles-only MVP text below:

* Launch always opens on the remembered store's list screen. It does not automatically present the store web sheet, even when the list was active earlier that day. The user enters the store through `Show Store` or by tapping a grocery row.
* The list header shows `Your list` on the left and a single store selector on the right. The store name uses a heavy, non-rounded system font, the store's configured primary color, and a small light pill. Do not show a duplicate selected-store label or put the title inside a list-row card.
* The selected store's configured `addedColor` is the source of truth for the list screen's accent/tint, including the store selector, `Show Store`, Add Items, and Pending/Added accents. Coles is RGB(224, 26, 34); Woolworths is RGB(0, 114, 61). The Show Store control uses a tinted Liquid Glass prominent button when available, with an earlier-iOS fallback, and has no separate grey bar behind it.
* The list footer places `Show Store` in the List's bottom safe-area inset, so the list scrolls clear of the button and `Clear List` is not covered. Keep the footer close to the bottom while preserving home-indicator clearance.
* The store overlay has a tappable collapsed bar that expands on tap or an upward vertical swipe. Its expanded navigation row preserves the original Back/status/right-action layout. The refresh glyph occupies the open trailing space, shifted slightly left for optical centring; hide it in the `All items handled` state.
* A detected retailer verification page pauses searches and progression. The error is a compact tappable status in the centre of the bottom controls; tapping opens a native confirmation dialog with full explanation, a cooldown-gated retry and Return to List. Do not repeatedly refresh a verification page. App-initiated store searches are paced and rapid selections coalesce to the latest search.
* The grocery input submits on Return/Enter. Pasted input can contain multiple lines and item separators include newline, comma, tab, and semicolon. Parsing occurs on submission/paste, not continuously while the user types.
* New items, and existing duplicates reactivated by typed input, move to the front of the visible list and shopping queue in their input order. Untouched items keep their relative order.
* In final-item Undo/Finish mode, all cards remain selectable. The active Added or Skipped card offers `Mark Pending`; selecting other cards preserves the final Undo/Finish controls until the user changes status, undoes, or finishes.
* Clear List has a full-width 56-point hit row. Its confirmation dialog is attached to that button so the system anchors the popover to the initiating control rather than the top of the screen.
* Woolworths remains detection-only (no cart Undo). Its quantity observation window is eight seconds to accommodate slower asynchronous web-component updates; Coles remains three seconds. This does not authorize any automated cart action. Live Woolworths verification remains a release check.
* New design work should bring the OpenPencil mockups into alignment with this implementation. Splash-screen alternatives are exploratory and do not imply an approved launch-screen design.

### Vision
ListRunner automates the tedious process of having to search for items on grocery websites when you already have the items recorded in your digital grocery list. The unique proposition is that it steps you through your whole list, one item at a time, on the store's real site.
ListRunner detects user actions but does not choose products, does not checkout, and does not manipulate payment/account details.

### MVP
The MVP is an app that imports or accepts a grocery list, uses Coles as the only supported store, opens that store in an in-app browser, overlays item cards, searches one item at a time, detects add-to-cart where supported, and allows manual progression when automation fails.

#### Platforms
* Native iPhone app supporting iOS 17 or later in portrait orientation.

#### MVP Architecture
* ListRunner is a native SwiftUI iOS app. The MVP does not use Capacitor or a web-app shell.
* Coles runs inside a persistent `WKWebView`, with the ListRunner overlay implemented as native SwiftUI.
* A generic store-automation engine and its JavaScript are bundled with the app. The engine reads bundled store configuration files and passes detected events to the native app through the `WKWebView` message bridge.
* The MVP bundles one store configuration for Coles. Automation scripts are injected only into the main frame of exact HTTPS hosts allowed by the active store configuration, using an isolated `WKContentWorld`. Native-issued session and interaction context is retained in that isolated world rather than exposed to the page's JavaScript environment. Subframes never receive automation or permission to send bridge events. Top-level links, redirects, or popups targeting non-allowlisted hosts open in Safari and do not receive ListRunner automation scripts.
* Store automation and configuration files are not downloaded remotely in the MVP.
* An automation session is scoped to one store. It has a unique session ID and separate search-automation and cart-detection capability states. Each capability has its own consecutive failed-item-interaction count and can be available or disabled for the session. In the MVP, the single Coles session begins when the app initializes store automation and ends on app termination or `Reset Coles Session`. It persists through web-view dismissal, navigation, and Coles sign-in/sign-out. Starting a new session makes both capabilities available and resets both failure counts.
* Apple Reminders integration uses the native EventKit framework.
* Lists, item state, search terms, source identifiers, and app-level launch metadata are persisted locally with SwiftData.
* A UI-independent native shopping-run state engine owns item status transitions, selected-item history, cooldown decisions, progression, completion, and undo restoration. SwiftUI views and the store-automation bridge send events into this engine rather than changing run state directly.
* The state engine processes shopping-run events serially in arrival order. Every delayed operation, including cooldown, search readiness, cart confirmation, quantity stabilization, cart reversal, reset, and persistence retry, receives a unique generation token. Each callback captures the applicable session ID, interaction ID, main-document generation, and operation generation for that operation; cancelling, completing, replacing, navigating away from, or otherwise invalidating an operation makes callbacks with stale context no-ops.
* The state engine produces updated state and explicit side-effect requests, such as searching the store or updating a linked reminder. Platform services execute those effects so progression rules can be tested without SwiftUI, `WKWebView`, SwiftData, or EventKit.

#### Accessibility
* ListRunner-owned list, settings, card, and overlay controls support Dynamic Type.
* ListRunner-owned controls expose meaningful VoiceOver labels, values, traits, and navigation order, including item status and selected state.
* When VoiceOver is active, presenting Coles, changing the selected item, or expanding the overlay moves focus to the selected card and announces the item name, displayed quantity, status, and position in the list. Collapsing the overlay moves focus to the collapsed bar, whose label includes the selected item and `Expand overlay`. Capability-warning badges and non-blocking error banners announce their message without moving focus away from the user's current control.
* ListRunner honors iOS Reduce Motion. Carousel changes move instantly or use a subtle crossfade, and the three-second cooldown uses non-continuous progress updates instead of sweeping animation. Reduce Motion does not otherwise change timing or state behavior.
* While VoiceOver or Switch Control is active, an add that would normally start cooldown enters an untimed added-confirmation state instead. `Undo` and `Next` remain available while that state is active; no automatic progression timer or countdown animation runs. The state exits when the user chooses `Undo` or `Next`, selects another item, collapses or dismisses the store, backgrounds the app, resets the session or list, or enters a recovery panel that invalidates the interaction. Other users retain the three-second cooldown unless they choose `Pause`, which also makes the current confirmation untimed. Unless a rule specifically concerns timer expiry or countdown presentation, cooldown status, undo, replacement, cancellation, collapse, and navigation rules also apply to the untimed state.
* ListRunner observes VoiceOver and Switch Control status-change notifications while a timed cooldown is active. Enabling either technology invalidates the timer generation immediately and converts that confirmation to untimed without changing its selected item, status, or Undo record. Disabling the technology does not restart timing for an already untimed confirmation; it remains untimed until the user acts or another documented cancellation transition occurs.
* These requirements apply to ListRunner's native interface; accessibility inside the Coles website remains controlled by Coles.

#### Appearance
* ListRunner's native list/summary and settings screens follow the system light or dark appearance using adaptive semantic colors.
* Overlay cards retain their defined brand gradients in both appearances, while overlay text and control surfaces use adaptive colors where possible.
* The Coles website controls its own appearance.

#### Features
* Support for https://www.coles.com.au. This is where we personally do most of our online shopping.
* Support exactly one active ListRunner list at a time.
* Parse raw text list of grocery items and quantities. Items are split on new lines, bullet markers, and commas, including comma-separated input such as `milk, bread, eggs`.
* Quantity parsing supports whole numbers, decimal amounts, multiplier forms, and common grocery units. Supported examples include `2 apples`, `2x apples`, `500g mince`, `1.5L milk`, and `3 cans tomatoes`.
* Parsing is best-effort. If ListRunner cannot recognize a quantity format, it preserves the full input as the item name, treats quantity as unspecified, and allows the user to correct the item from the list/summary screen. Unrecognized input is not rejected or silently discarded.
* Blank entries and entries containing only bullet characters or whitespace are ignored.
* Stored item names preserve the user's or source's capitalization after surrounding whitespace is trimmed and repeated internal whitespace is collapsed. Manual edits preserve the capitalization entered by the user.
* The overlay formats item names in sentence case for display without changing the stored item name. Coles searches use the stored item name rather than the formatted overlay text.
* The overlay formatter uppercases recognized acronyms. The MVP recognized-acronym list includes `BBQ`, so `bbq sauce` is presented as `BBQ sauce`.
* When users type or paste multiple items into a non-empty list, the parsed items are appended as new `Pending` items in their input order. Existing items are not replaced.
* Duplicate-name normalization ignores capitalization, trims surrounding whitespace, and collapses repeated internal whitespace. For example, `Milk`, `milk`, and ` milk ` match the same normalized item name.
* Typed or pasted items with the same normalized item name are automatically merged into one ListRunner item instead of creating duplicate entries.
* When merged duplicate items have quantities with the same normalized quantity unit, their amounts are added together. For example, `2 apples` and `3 apples` become one item displayed as `5 apples`. The MVP does not convert between different units.
* When one duplicate has no specified quantity and the other has a specified quantity, the specified quantity replaces the unspecified value. The display fallback of `1` is not included in the sum. For example, `apples` and `2 apples` become `2 apples`.
* Items with the same normalized name but incompatible quantity units remain separate. For example, `2 cans tomatoes` and `500g tomatoes` are not merged.
* When typed or pasted input merges into an existing item, the merged item has `Pending` status regardless of whether it was previously `Pending`, `Added`, or `Skipped`. For a linked Paprika item, the merged name and quantity update the linked reminder text and the status transition unchecks the reminder. Paprika reminders with duplicate reminder IDs remain ignored instead of being merged.
* Overlay item cards over store website for wizard like navigation.
* Stepping through grocery items
* Ability to skip to a specific item by clicking on the item's card.
* If at least one `Pending` item remains after an item is added to the cart, a three-second cooldown starts, allowing the user to undo adding to cart if they added the wrong item or need to add multiple of the same item. If VoiceOver or Switch Control is active, the corresponding added-confirmation state is untimed as specified under Accessibility. If supported, the undo function will reverse the adding of the item to the store cart. Undo always rolls back ListRunner’s state; store cart rollback is best-effort only. When an add handles the final pending item, ListRunner instead enters the persistent final-item confirmation state defined under Progression Rules.
* Another automatic add while a timed or untimed added-confirmation state is active replaces the transient `Undo` target with the item's current `Added` state and leaves the item `Added`. The three-second timer restarts for timed cooldown; the untimed state remains untimed. Therefore, `Undo` after a later add reverses only the latest add on a best-effort basis and leaves the ListRunner item `Added`.
* A detected quantity increase above the previous correlated Coles quantity is treated as another automatic add, marking the item `Added` and starting or restarting cooldown when pending items remain, unless the selected item is paused or the confirmation is already untimed. In either untimed case, the latest add updates the Undo target without starting a timer.
* A detected removal or quantity decrease is treated as the newest cart event and cancels any active cooldown, discarding the stale `Undo` target. ListRunner tracks the latest confirmed quantity for each store product associated with the selected item during the active run. When processing a confirmed store event, the item stays `Added` while any associated product has a quantity above zero and returns to `Pending` only when every associated product has a confirmed quantity of zero. This aggregate rule is a store-event transition rule, not a continuously enforced invariant; a later ListRunner-only action such as `Undo` or editing may intentionally set a different local status without changing Coles.
* Selecting another item during cooldown cancels the cooldown, keeps the previously selected item in `Added` status, and immediately searches the newly selected item when search automation is available; otherwise it selects the item without changing the Coles page.
* Clicking a next button to skip the cooldown.
* Marking items as added manually, particularly useful when automation is not available or not working correctly.
* Skipping items
* Ability to import from Reminders on Apple systems from a list called `Paprika`. Paprika exports grocery lists to Apple Reminders. ListRunner reads incomplete reminders from that list and imports each reminder title as grocery-list input. Reminder notes and other fields are ignored.
* Items that do not have any specified quantity will display as a quantity of '1' in the overlay without any quantity unit.
* Item quantity is display guidance only. ListRunner does not automatically set or enforce the quantity in the Coles cart.

###### On supported grocery sites -
* Automatic search triggering and item progression when items are added to cart.
* Observe direct user interaction with the store's add item button, store numerical add-to-cart field, or store add-additional-item button (typically depicted with a plus icon) as a candidate add for the currently selected ListRunner item. The user may manually refine the Coles search or navigate within Coles without editing the ListRunner item or breaking that association. The interaction alone is not confirmation; ListRunner automatically progresses only after a matching confirmed cart quantity change or other supported cart signal within three seconds.
* Observe direct user interaction with the store's remove button, typically depicted with a minus icon, or store quantity field as a candidate removal. A matching stable quantity decrease confirms the removal. When one product's resulting quantity reaches zero, that Coles product control returns to its red `Add` state. ListRunner returns the selected item to `Pending` only when every store product associated with that item has a confirmed quantity of zero; otherwise the item remains `Added`.

#### Paprika Import
ListRunner requests Apple Reminders permission only when the user first selects the Paprika import action, not on app launch.
After the user selects import, the action is disabled and displays `Importing…` until that attempt finishes; repeated taps do not start additional imports. On completion or failure, the normal import action becomes available again.
ListRunner matches the Reminders list name exactly and case-sensitively as `Paprika`. If more than one accessible list has that exact name, ListRunner imports nothing, shows `Multiple Paprika lists found`, and leaves the current ListRunner list unchanged.
Each incomplete reminder title is processed through the same item-name and quantity parser used for typed input. Blank titles and titles containing only bullet characters or whitespace are ignored. Reminder notes do not affect the imported item.
An imported Paprika reminder is checked when its ListRunner status changes to `Added` after manual `Mark Added` or automatic add detection. The reminder is unchecked when its ListRunner status changes to `Pending` or `Skipped`, including when `Undo`, editing, merging, or detected cart removal causes that transition.
When Paprika is imported into an existing ListRunner list, incomplete reminders whose reminder IDs are already present in the list are ignored. New reminders are sorted by creation date from oldest to newest, with reminder ID as the deterministic tie-breaker, then imported as new `Pending` items and appended to the end of the ListRunner list in that order. Reminders without a creation date sort after dated reminders and use reminder ID ordering among themselves.
Successful imports update the visible ListRunner list without showing a separate success message.
Paprika import is snapshot-based and one-way after import. External edits, completion, or deletion in Apple Reminders do not change the existing ListRunner item. Re-importing adds new incomplete reminder IDs but does not refresh existing items. ListRunner may write the current item name and quantity to a linked reminder and synchronizes its checked state from ListRunner status: `Added` is checked, while `Pending` and `Skipped` are unchecked.
Reminder writeback is best-effort. If a linked reminder no longer exists or an EventKit write fails, ListRunner keeps the local text and status change, does not retry, and does not block or interrupt shopping.

Paprika import first reads and validates the complete reminder snapshot, derives the ordered set of new items, and stages the entire import before changing the active list. The staged items are committed in one local transaction and become visible together only after that transaction saves successfully. If the local transaction fails, no imported item becomes visible, the previous list remains unchanged, and ListRunner shows `Could not import Paprika reminders`; the import action becomes available for a new attempt.

Every linked-item mutation records the desired reminder text and checked state for the same local state revision. The persistence coordinator releases that EventKit write only after the corresponding local revision is saved successfully. Writes are serialized per reminder ID and coalesced to the latest desired revision that has not started. If an older write is already in flight, the latest desired revision runs after it finishes so an older completion cannot become the final Reminder state. Deleting the item cancels queued writes. An EventKit failure is not retried for that revision, although a later user mutation may make one new best-effort attempt for its newer revision. Queued or in-flight writeback is transient and may be lost if the app terminates; local ListRunner state remains authoritative.

#### Core user flow
Import or type list → review list → `Show Store` → ListRunner searches current item → user adds product → ListRunner detects add → cooldown when another pending item remains → next pending item.
* If automation fails, the user can search manually, mark added manually, or skip.
* On opening ListRunner mobile, the user is presented with a space to type a grocery list of items or add items one by one. They also have the option to add items from Paprika.
* Multiline or pasted raw text is parsed only after the user taps an explicit `Add Items` action. Parsed entries are added directly to the editable list; ListRunner does not show a separate parse-preview step or parse and modify the active list continuously while the user is typing.
* `Add Items` is also used for one-item manual entry. One non-empty item creates one `Pending` item; multiple parsed entries create or merge items in input order. Submitting blank or bullet-only input leaves the active list unchanged. After at least one item is added or merged successfully, the raw-input field is cleared.
* On the Your list screen, an Edit control enables native iOS row reordering: the whole row lifts and follows the user's finger or pointer until dropped. Reordering persists immediately, changes no item status, and the new order is used by the shopping carousel and progression.
* The grocery-row actions menu offers `Mark Added` for Pending items and `Mark Pending` for Added items. These update ListRunner status and persist immediately without changing the Coles cart; Skipped items retain their existing status-specific actions.
* `Show Store` presents the Coles web view and item-card overlay over the list/summary screen. The Coles web view fills the full width of the presented sheet and extends to its top edge, so the store's own content begins at the top and is never covered by a fixed native header or close button. A native drag handle sits over the sheet's top edge; pulling down from the handle dismisses the presented web view and returns to the list. The handle exposes an accessible `Dismiss store` action. Pulling down on the ListRunner overlay collapses it; a gesture beginning in Coles web content never dismisses the store, so ordinary page scrolling is unaffected.
* Adding or importing the first items keeps the user on the list/summary screen so they can review the parsed list before showing the store.

#### Persistence and resume
ListRunner persists a non-empty grocery list, item quantities, item statuses, the last item selected in the overlay, search terms, and Paprika reminder identifiers. A separate app-level metadata record persists the optional last-active local calendar date even when no grocery list exists.
Every local state mutation receives a monotonically increasing nonnegative 64-bit integer revision. The last saved revision is stored with the local state, and a new process continues from the saved value. A dedicated persistence coordinator serializes saves so at most one snapshot is being written at a time. Mutations arriving during a save are coalesced into the newest snapshot; after the in-flight save completes, the coordinator immediately saves the newest revision if it is still outstanding. Save completion for revision R can advance the persisted revision only to R and can never mark a newer revision durable.
If a SwiftData save fails, ListRunner keeps the newest in-memory state so shopping can continue and shows a persistent non-blocking `Changes may not be saved` banner. The next state-changing action and foreground transition request a retry of the newest revision, never the failed historical snapshot. The banner disappears only when the persisted revision equals the latest requested revision. If the app terminates first, changes after the last successful revision may be lost.
If the SwiftData store cannot open or migrate at launch, ListRunner does not create a replacement store silently. It shows a blocking `Could not load ListRunner data` recovery screen with `Retry` and `Reset Local Data`. `Retry` attempts to open and migrate the existing store again. `Reset Local Data` requires confirmation, removes only ListRunner list, app-metadata, and diagnostics storage, then creates an empty store; it does not change Apple Reminders or Coles website data.
The in-app Coles browser uses persistent website storage so Coles cookies, login state, and cart data can survive app launches as supported by the Coles website. ListRunner does not read or manage the user's Coles credentials.

* A secondary settings area remains accessible on the list/summary screen whether the list is empty or non-empty. `Reset Coles Session` is available there and requires confirmation. After confirmation, ListRunner immediately enters a `Resetting…` state, cancels any cooldown or final-item confirmation, invalidates the active interaction and automation session IDs, gates bridge messages from the old session, disables store presentation, and then clears Coles cookies and local website storage. Cancelling final-item confirmation for reset discards its transient Undo record and leaves the persisted item status unchanged. Only after clearing succeeds does ListRunner create a new automation session and load `https://www.coles.com.au` without presenting the web view. It preserves the ListRunner list, statuses, and selected item, signs the user out locally, and does not clear Apple Reminders. It does not guarantee deletion of a server-side Coles cart, which may return after the user signs in again. `Show Store` later presents the reset web view. If clearing cannot be confirmed, ListRunner shows `Could not reset Coles session` with `Retry` and `Cancel`. `Retry` repeats the clear operation while the store remains hidden. `Cancel` dismisses the error, creates a fresh automation session using whatever Coles website data remains, and restores `Show Store`; ListRunner does not claim that the session data was cleared.
* `Clear Diagnostics` is available in the same settings area. It immediately deletes all ListRunner diagnostic entries without confirmation and shows `Diagnostics cleared`. It does not change the grocery list, app metadata, Apple Reminders, Coles website data, or the automation session. Repeated clearing is safe when no diagnostics exist.

* On launch, ListRunner first reads the saved last-active local calendar date and last overlay-selected item ID without updating either value. If a non-empty list has at least one `Pending` item and a saved date matching today's local calendar date, it presents the Coles web view over the list/summary screen, restores the saved selected item, creates a fresh interaction ID, and searches that item. If that item was deleted or no selection was saved, it uses the normal first-item or deletion fallback and searches the resulting selection. If the list is empty, complete, the saved date is missing, or the saved date differs from today, ListRunner keeps the list/summary screen visible and does not present the web view. After choosing the launch destination, ListRunner saves today's local calendar date.
* The list/summary screen remains underneath the presented Coles web view. Pulling down from the native sheet's top drag handle dismisses the web view, reveals the list without changing selection or item status, invalidates the active interaction ID, and causes delayed bridge messages for that interaction to be ignored. The handle exposes the accessible action `Dismiss store`; no fixed close button is placed over the Coles page because its top content is controlled by the embedded website. Dismissal preserves the Coles page, website storage, automation session, and any final-item confirmation; when that confirmation exists, the revealed list shows its `Undo` and `Finish` banner.
* `Show Store` presents the Coles web view, returns to the last item selected in the overlay, and creates a fresh interaction ID. It searches the item when search automation is available; otherwise it leaves the current Coles page unchanged for manual searching. If the overlay has not been used for the current list, `Show Store` selects the first item in list order and applies the same capability-dependent search rule.
* Dismissing and reopening the Coles web view does not reset the active automation session or either session capability. A capability disabled for the session is retried only when a new Coles session starts, such as after `Reset Coles Session`; the other capability continues operating independently while available.
* When the app enters the background, ListRunner cancels any active cooldown, preserves final-item confirmation when present, keeps the current item status, suspends automation, invalidates the active interaction ID, and ignores bridge messages while inactive. The current Coles page, website storage, and automation session remain preserved. If the Coles web view is still presented when the app returns to the foreground, ListRunner creates a fresh interaction for the selected item and re-establishes product quantity baselines from the current page without forcing a new search. Final-item Undo retains its recorded provenance, but store reversal remains allowed only if the session, document, product, and current quantity still satisfy the normal safety checks.
* `Show Store` is hidden only while the list is empty and remains available for a completed non-empty list so the user can inspect the Coles cart or store session.
* The presented Coles sheet has rounded top corners, including expanded, collapsed, fallback, recovery, and confirmation states. Use the native iOS sheet's system corner treatment in the app; the design reference uses 32-point top-left and top-right radii, with the web surface clipped to the sheet outline. Keep the top drag handle visible. Do not clip the overlapping item cards at the separate lower overlay-panel boundary.
* Tapping an item on the list/summary screen selects that item, opens the shopping website overlay, and immediately searches for it on Coles when search automation is available. If search automation is disabled, it opens the overlay without changing the Coles page. The item's status does not change until the user takes a status-changing action.
* Whenever the selected item changes while the Coles web view is presented, ListRunner creates a fresh interaction ID and immediately searches the newly selected item when search automation is available; otherwise it leaves the current Coles page unchanged for manual searching. This applies to card selection, `Back`, `Next`, `Skip` progression, cooldown completion, and any visible-overlay selection fallback. Selection changes while Coles is hidden update and persist selection without searching; the next `Show Store` creates the interaction and applies the same capability-dependent search rule.
* The list/summary screen preserves list order rather than grouping items by status. Each row displays its status badge, and summary counts for `Pending`, `Added`, and `Skipped` appear above the list.
* Non-blocking import, persistence, and cart-undo notices use compact native SwiftUI compositions: a neutral grouped surface, a semibold heading, secondary explanatory text, and a standard dismiss button with at least a 44-point hit target where dismissal is allowed. Preserve each notice's existing wording, lifetime, and dismissal rules; persistence warnings remain non-dismissible. There is no assumed system error-banner API. Use the system alert presentation for recovery decisions such as failed store loading or failed Coles-session reset, retaining their documented actions. Inline field validation remains attached to the affected field rather than becoming a modal alert.
* On list screens with notices, place the entry controls, totals, grocery rows, and list footer in scrollable content clipped above the fixed Show Store action. Provide sufficient bottom padding to scroll every row and footer action fully into view. Notices must not cause content to draw over or obscure Show Store; support Dynamic Type through content growth and scrolling rather than shrinking text to fit.
* The list/summary screen displays a `Complete` indicator when no items have `Pending` status.
* Users can add items to an existing list, including a completed list. Each new item begins with `Pending` status, causing the `Complete` indicator to disappear and normal overlay progression to resume.
* Users can open an item's inline edit mode from the list/summary screen and edit its name, numeric quantity amount, and optional quantity unit. `Save` validates and applies all fields atomically; `Cancel` discards every change and closes edit mode. A blank item name keeps edit mode open, shows `Item name is required`, and focuses the name field. The quantity amount accepts only valid whole or decimal numbers; an invalid amount keeps edit mode open, shows `Enter a valid quantity`, and focuses the amount field. VoiceOver announces either validation error when it appears. The quantity unit is free text with suggestions including `g`, `kg`, `mL`, `L`, `cans`, and `packs`; it is trimmed but otherwise preserved. Saving with a blank quantity amount also clears the unit, stores the quantity as unspecified, and makes the overlay display the fallback quantity `1` without a unit. A unit without an amount does not create a quantity. A valid save updates the Coles search term when the item name changed, affects only that row, and never automatically merges it with another existing item, so editing may create duplicate normalized names. If no pending items remain, ListRunner selects the next remaining item in list order, or the previous item if the deleted item was last. If the list becomes empty, no item is selected. References to the deleted item are removed from `Back` selection history.

* `Clear List` is available on the list/summary screen whenever the list is non-empty, not only when reopening an older run.
* `Clear List` removes the saved list and shopping-run state from ListRunner only. It does not change Apple Reminders, the Coles cart, or the in-app browser's stored Coles session.
* If at least one item is `Pending`, `Clear List` requires confirmation before removing the list. If no items are `Pending`, the list is already marked `Complete` and `Clear List` proceeds without a confirmation dialog.
* Active cooldown timers, manual pause, final-item confirmation, `Back` selection history, capability failure state, unconfirmed warnings, and store-product associations are transient and are not restored after the app is terminated. Termination while final-item confirmation is active accepts the persisted `Added` status and discards its Undo record, so a later launch treats the list as complete.

#### Acceptance criteria
* Given a list of 10 items, the user can import it, show Coles, search each item, mark items added manually, skip items, and handle every item without being blocked by automation.
* The bundled Coles configuration automatically searches the selected item and detects supported add and removal/quantity changes on the live Coles website.
* If automatic search, add detection, or removal detection fails, manual fallback still allows the user to navigate the list, use the Coles site directly, mark items added, skip items, and reach `All items handled`.
* If the Coles web view cannot load or its web-content process terminates, ListRunner preserves the shopping run, makes no item-status change, and presents native `Retry` and `Return to List` recovery actions.
* With Reminders permission granted and a `Paprika` list present, ListRunner imports new incomplete reminders without duplicates, updates linked reminder text after ListRunner edits, checks the linked reminder when its item becomes `Added`, and unchecks it whenever the item becomes `Pending` or `Skipped`.
* Release diagnostics remain on-device, contain only the allowed diagnostic fields, expire after 168 hours, remain within the specified count and byte caps, and can be deleted immediately with `Clear Diagnostics` without affecting the list, Reminders, Coles data, or the automation session.
* Relaunching on the same local calendar day with `Pending` items restores the persisted list, statuses, edits, Coles web view, and last overlay-selected item. Relaunching on the same day with a completed list, or on a later day, preserves the same run but opens the list/summary screen first. The saved date is compared before it is updated, and today is saved only after the launch destination has been chosen. Cooldown, `Back` history, capability failure state, and unconfirmed warnings are not restored, while the independent Coles website session remains persistent.

### Fallback & Error Handling
If either automation capability is unavailable, the user can still move through items manually and use `Mark Added`. The overlay shows a small capability-specific badge that says which function is unavailable while any unaffected capability continues operating. When only search is unavailable and normal Back / Skip or Back / Next navigation is shown, place the warning symbol and `Search unavailable` label in the centered space between those buttons, replacing `Swipe cards to browse`; do not add a separate message area. Use readable secondary text and a system warning symbol rather than a large red panel, with a minimum 44-point-high tap target that opens the scope-specific explanation below using a native presentation. Countdown, untimed or paused confirmation captions, final-item confirmation, and completion messaging take priority in that space; in those states retain a small accessible warning indicator beside the priority caption, without covering controls or changing their actions. Announce a newly unavailable capability without moving VoiceOver focus. Save failures and cart-undo errors remain separate non-blocking notices with their existing lifetime and dismissal rules.
The user's Coles login state does not determine capability availability. Automation continues while the store page permits the required search and cart actions.

#### Capability fallback scope
* Search automation and cart detection fail independently. Each capability has an interaction outcome of `notAttempted`, `pending`, `failed`, `succeeded`, or `cancelled`. Starting an eligible attempt changes `notAttempted`, `failed`, or `succeeded` to `pending`. A matching success before its deadline changes it to `succeeded`, clears that capability's interaction warning, and resets only that capability's consecutive session failure count. A terminal timeout or typed interaction failure changes it to `failed`. Cancelling a still-pending operation because the user leaves the interaction changes it to `cancelled` and does not count as a failure.
* A later eligible cart attempt within the same interaction may replace a failed cart-detection outcome with `pending` and then `succeeded`. A search timeout invalidates that search-operation generation; a late `searchReady` is ignored, and search is retried only in a fresh interaction. Passive quantity observations after a failed cart window update baselines but do not turn the outcome into success.
* An interaction ends when selection changes, the store is dismissed, the app backgrounds, a recovery panel invalidates the interaction, the list or Coles session is reset, or the app terminates. Same-domain manual navigation retains the interaction but invalidates callbacks from the previous document generation. At interaction end, a capability's session failure count increments once only when its final outcome is `failed`; `succeeded` leaves its already-reset count at zero, while `notAttempted` and `cancelled` leave the count unchanged. Two consecutive failed interactions for one capability disable only that capability for the rest of the Coles session; the other capability and its count are unaffected.
* An interaction-scoped failure applies only to the reported capability and interaction ID. Creating a fresh interaction, including returning to the same item after selecting another or using an explicit retry, clears interaction-scoped warnings and retries each capability that remains available for the session.
* An `automationUnavailable` event declares a capability of `search`, `cartDetection`, or `all` and a scope of `interaction` or `session`. An interaction-scoped event shows the corresponding warning for the active interaction. A session-scoped event immediately disables the declared capability. Configuration failure, script-injection failure, or unavailable bridge capability uses capability `all` with session scope and disables both capabilities immediately.
* Failures detected by native code before a bridge script can run, including configuration decoding and script-injection setup failures, are sent directly to the state engine as typed capability events and do not fabricate a bridge message or require document, interaction, item, or page-URL fields.
* When search automation is disabled for the session, selecting an item updates the overlay and creates a fresh interaction but does not initiate a Coles search; the user searches with the Coles search bar, and cart detection continues if available. When cart detection is disabled, automatic search continues if available, and the user uses `Mark Added` after changing the Coles cart. Dismissing and reopening the web view does not end the store session or clear either disabled capability.
* The badge label is `Search unavailable` when only search automation is unavailable, `Cart detection unavailable` when only cart detection is unavailable, and `Automation unavailable` when both are unavailable. For an interaction-scoped search failure, the tooltip says `ListRunner couldn't search for this item. Search in Coles, then continue with the overlay.` For an interaction-scoped cart-detection failure, it says `ListRunner couldn't confirm cart changes for this item. Use Mark Added after adding it in Coles.` Session-scoped tooltips replace `for this item` with `for this Coles session` and add `Reset the Coles session to retry.` When both capabilities are unavailable, the tooltip combines the applicable manual-search and `Mark Added` guidance. VoiceOver announces the badge label and tooltip when the warning first appears without moving focus.
* The centered navigation-warning placement also applies to `Cart detection unavailable`: replace the browsing hint between Back / Skip or Back / Next, remove the separate message strip, and allow the label to wrap to two centered lines without reducing readable text size. Tapping the 44-point-high target opens the cart-detection explanation above. Confirmation/countdown/completion messages retain priority, with the same accessible warning-indicator fallback as search failure; unaffected search automation continues normally.
* Use the same centered placement for `Automation unavailable` when both capabilities are unavailable, replacing the browsing hint without a separate warning strip. Allow two centered lines and a 44-point-high tap target that opens the combined manual-search and Mark Added explanation. The same confirmation/countdown/completion priority and accessible warning-indicator fallback apply.

#### Possible failure cases
* Store page cannot load.
  * An offline, DNS, TLS, or top-level navigation failure cancels any active cooldown, keeps the current item status, invalidates the active interaction ID, and shows a native error panel with `Retry` and `Return to List`. `Retry` attempts the intended Coles URL again without changing ListRunner state. `Return to List` dismisses the web view and reveals the preserved list/summary screen.
  * If the initial Coles load fails, the error panel appears over a neutral web-view background. If a later navigation or reload fails while a previously rendered Coles page remains available, that page may remain visible behind the panel.
* Coles web-content process terminated.
  * ListRunner cancels any active cooldown, keeps the current item status, invalidates the active interaction ID, and shows the same native error panel over a neutral background. `Retry` rebuilds the `WKWebView`, preserves website storage where supported, creates a fresh interaction for the selected item, and loads the intended Coles URL. `Return to List` reveals the preserved list/summary screen.
* Local save failed.
  * ListRunner keeps the in-memory shopping state available, shows `Changes may not be saved`, and retries on the next state change and foreground transition without blocking store or list interaction.
* Local data cannot load or migrate.
  * ListRunner blocks normal app entry and shows `Could not load ListRunner data` with `Retry` and confirmed `Reset Local Data` recovery. Reset affects only ListRunner storage and leaves Apple Reminders and Coles website data unchanged.
* Store automation unavailable
  * If either capability reaches its two-consecutive-failed-item threshold, ListRunner disables that capability for the session and shows its capability-specific badge. If the active store configuration fails to load or scripts cannot be injected, ListRunner disables both capabilities and shows `Automation unavailable`. The badge tooltip explains which manual actions remain available.
* Search is not loading
  * ListRunner waits up to ten seconds for the Coles results page to become recognizable after starting automatic search. If it does not, the item remains `Pending` and receives the interaction-scoped `Search unavailable` warning. The user can search with the Coles search bar, use `Mark Added` after finding the item, or press `Skip`. ListRunner retries search automation on the next interaction while the search capability remains available; cart detection continues independently.
* Add-to-cart cannot be detected
  * ListRunner cannot know with certainty that add-to-cart detection has failed. If a likely add-to-cart interaction does not produce a confirmable cart signal within three seconds, the current item receives the interaction-scoped `Cart detection unavailable` warning.
  * The badge tooltip explains that ListRunner could not confirm the cart change. The user can still add the product on the store website and tap `Mark Added` in the overlay. Manual marking updates ListRunner only and advances immediately without cooldown when Pending items remain; the final item instead retains Undo / Finish. ListRunner retries cart detection on the next interaction while that capability remains available; automatic search continues independently.
* Reminders permission denied.
  * ListRunner shows `Could not access Paprika reminders` and leaves the current list unchanged. The message does not include an `Open Settings` action. The import action becomes available again so access can be retried after the user changes permission externally. Typed, pasted, and manually added grocery lists remain fully available.
* Reminders access restricted, revoked, or read failed.
  * ListRunner shows `Could not access Paprika reminders`, leaves the current list unchanged, and makes the import action available again. The failure does not block typed, pasted, or manually added grocery lists.
* Paprika list not found.
  * ListRunner shows `Paprika list not found` and leaves the current ListRunner list unchanged.
* Multiple Paprika lists found.
  * If more than one accessible Reminders list is named exactly `Paprika`, ListRunner shows `Multiple Paprika lists found` and leaves the current ListRunner list unchanged.
* No new Paprika items.
  * If the Paprika list contains no new incomplete reminder IDs to import, ListRunner shows `No new Paprika items` and leaves the current ListRunner list unchanged.
* Reminder writeback fails.
  * ListRunner keeps the local change and continues without retrying or interrupting the shopping session.

### Store Website Overlay

ListRunner displays a native wizard overlay on top of the grocery store website, anchored to the bottom of the screen. The store remains visible and interactive outside the area covered by the expanded overlay, and collapsing the overlay exposes the covered store controls while preserving ListRunner context.

Pulling down on the expanded overlay card collapses it into a compact bottom bar that shows the selected item and exposes the Coles page behind it. Pulling up on the collapsed bar, tapping the bar, or using its `Expand overlay` accessibility action restores the expanded overlay. The expanded card exposes a `Collapse overlay` accessibility action. Collapsing or expanding does not by itself change item status, selection, product associations, the active interaction ID, or the Coles automation session. Collapsing during cooldown cancels the cooldown and discards its undo target while keeping the item `Added`. Collapsing during final-item confirmation preserves that confirmation and its Undo record; expanding restores its `Undo` and `Finish` controls. A confirmed add while the overlay is collapsed automatically expands the overlay and starts a fresh cooldown when another `Pending` item remains. Only a pull-down beginning on the native top drag handle dismisses the presented web view; the handle also exposes an accessible `Dismiss store` action. Pull-down gestures in Coles web content retain normal website scrolling behavior, and no fixed close button is placed over the web content.

The overlay contains a horizontal carousel of portrait item cards with the standard playing-card 5:7 width-to-height ratio. On a 402-point-wide iPhone canvas, the selected card is nominally 160 × 224 points; non-selected cards scale proportionally and remain the same 5:7 ratio. The carousel is vertically aligned to the top edge of the ListRunner overlay panel so each card straddles that boundary, with approximately half of the card over the Coles web view and half over the overlay. Cards remain fully visible and are not clipped at the panel edge. Smaller neighboring cards are bottom-aligned with the selected card. The selected card is centered and visually emphasized with a colored gradient, item name, and quantity. Pending and Skipped selected items offer Mark Added. Added items offer Pause during an active timed automatic-add confirmation, with the VoiceOver hint `Stop automatic progression. Continue with Next when ready.` Outside timed cooldown they offer Mark Pending in the same button position, except during final-item confirmation. The VoiceOver hint is `Marks this grocery item pending in ListRunner only. Does not remove it from your Coles cart.` Every skipped item displays a small Skipped badge in its top-left corner. Non-selected added items appear as smaller green cards with an Added label and quantity. Upcoming pending items use the cream gradient. Colour changes animate smoothly between states.

Below the card carousel are large navigation controls:
- `Back` returns to the last selected item without changing item status. It remains visible but is disabled with reduced contrast when selection history is empty.
- `Skip` is shown when the selected item is `Pending` and skips that item.
- `Next` is shown when the selected item is `Added` or `Skipped` and at least one `Pending` item remains. It advances to the next pending item.
- The user can also tap any visible item card to jump directly to that item and immediately search it on Coles when search automation is available; otherwise the selection changes without changing the Coles page.

During an active cooldown, `Back` is unavailable and `Undo` is shown as a temporary action. `Next` remains available to skip the cooldown. When cooldown ends or is cancelled, `Undo` disappears and `Back` returns.
Choosing `Pause` during an automatic-add countdown converts it to untimed confirmation, preserving Undo and showing `Paused · Next when ready` between Undo and Next. The card button becomes Mark Pending afterward. There is no Resume action or automatic timer restart. Revisiting an Added item shows Mark Pending with normal Back / Next navigation and no paused caption.
Tapping another visible item card during cooldown remains allowed. It cancels the cooldown, keeps the previously added item in `Added` status, selects the tapped item, and immediately searches it on Coles when search automation is available; otherwise it leaves the Coles page unchanged.

When final-item confirmation is active, the final item remains selected, `Undo` and `Finish` replace normal navigation, and `Back` plus all card-selection actions are disabled until the user resolves the confirmation. Closing the store preserves the confirmation and shows a native list-summary banner with the same `Undo` and `Finish` actions; reopening the store returns to the final selected item and confirmation controls. The state also survives overlay collapse and app backgrounding within the current process.

The shopping-session overlay does not have a separate start or end screen. When no items have `Pending` status and final-item confirmation is not active, the right-hand `Skip`/`Next` control is replaced by the message `All items handled` with the supporting text `Continue to checkout when ready.` The carousel and `Back` control remain available so the user can select earlier items and make changes. If an item returns to `Pending` status, the normal progression control returns.

The overlay should feel like a lightweight shopping assistant, not a replacement for the store website. The user still selects products and interacts with the real store page; ListRunner only guides the sequence of searches, tracks progress, and provides manual fallback controls when automation fails.

### Store Automation Configs
The MVP uses a generic bundled automation engine with one bundled Coles configuration. The configuration schema is designed so additional grocery websites can use the same engine without changing the core shopping workflow.

Each store configuration defines:
- Schema version.
- Store identifier and display name.
- Supported domains and navigation policy.
- Search URL pattern.
- CSS selectors and strategies for add-to-cart detection.
- CSS selectors and strategies for quantity and removal detection, when available.
- Ordered selector, attribute, nearest-product-link, and product-page-URL rules for extracting a stable store product identifier.
- Manual fallback behavior.

The MVP automation engine supports these named strategies:
- URL-template search, which percent-encodes the selected item's search term into a configured URL.
- Selector-based add detection, which recognizes interaction with configured add buttons or quantity inputs.
- Quantity-value observation, which watches configured quantity controls and classifies a stable committed value as an add, remaining-added quantity, or removal to zero. The initial observed value establishes a baseline without emitting an event, repeated reports of the same resulting value are ignored, and one physical cart change produces at most one ListRunner transition.
- Stable product-ID extraction, which first uses a configured direct element attribute when present, then the nearest product link inside the same enclosing result tile, and finally the current product-detail page URL for a page-level control. A link or page URL is accepted only when URL resolution produces an exact allowlisted HTTPS Coles host and a pathname matching `/product/<non-empty-slug>-<numeric-id>`; the terminal numeric suffix of the final pathname component is the product ID, and query or fragment text is not part of it. The Coles configuration uses the nearest-link rule for search-result controls because the current Coles tile and add button do not expose a direct product-ID attribute. Extraction is repeated from the current DOM after an add button rerenders into quantity controls, and it must stay within the same enclosing tile rather than searching another result. If no stable ID can be extracted for a candidate cart interaction, the script emits interaction-scoped `automationUnavailable` for capability `cartDetection` with reason `productIdUnavailable`, does not arm a confirmation window, and leaves search automation available.

Injected JavaScript communicates with native Swift through versioned JSON bridge messages. The bundled script serializes each message to a JSON string before posting it; native code requires `WKScriptMessage.body` to be a string, measures that string's UTF-8 representation, rejects it above 8 KiB, and only then decodes it. Every bridge message requires the current schema version, event type, store identifier, automation session ID, native-issued main-document generation, and current page URL. Interaction-scoped messages also require the active interaction ID and ListRunner item ID. For the current schema version, native decoding rejects unknown fields, wrong types, non-finite numbers, out-of-range values, unsupported enum cases, and missing or forbidden event-specific fields.

The MVP bridge contract is:

| Event | Additional required fields | State effect |
|---|---|---|
| `cartInteractionStarted` | Interaction ID, item ID, store product ID, observed quantity before interaction, and intent of `add`, `increment`, `decrement`, or `setQuantity` | Arms or replaces the native three-second cart-confirmation window; never changes item status by itself. |
| `addDetected` | Interaction ID, item ID, store product ID, and resulting quantity | Updates the product baseline and confirms an add only when it is a stable increase matching the active armed window. |
| `quantityChanged` | Interaction ID, item ID, store product ID, and resulting quantity | Always updates the product baseline; changes ListRunner status only when the stable delta matches the active armed window. |
| `removalDetected` | Interaction ID, item ID, store product ID, and resulting quantity | Updates the product baseline and confirms removal only when it is a stable decrease matching the active armed window. |
| `searchReady` | Interaction ID, item ID, and search-operation generation | Completes only the matching active automatic-search operation and never changes item status. |
| `automationUnavailable` | Typed reason, capability of `search`, `cartDetection`, or `all`, and scope of `interaction` or `session` | Applies capability fallback. Interaction ID and item ID are required only for interaction scope and omitted for session scope. |

The common fields and the additional fields listed for one event form that event's complete field whitelist; every other event-specific field is forbidden. Store product ID and cart intent are forbidden on events that do not concern a product. Observed-before quantity is required only on `cartInteractionStarted`; resulting quantity is required only on `addDetected`, `quantityChanged`, and `removalDetected`; search-operation generation is required only on `searchReady`. Both quantity fields are finite whole numbers from 0 through 9,999. Reason, capability, and scope are forbidden except on `automationUnavailable`, and valid reason/capability/scope combinations are closed enums in the native model. The Coles product ID is 1 through 32 ASCII digits whether read from a configured direct attribute or URL suffix.

The bundled isolated-world script emits `cartInteractionStarted` only from a capturing listener when `Event.isTrusted` is true, the event targets a configured cart control, a valid stable product ID can be extracted from that control's own tile or product page, and the control's current quantity can be read or inferred as zero from its configured not-in-cart state. Native code validates the message and creates a new confirmation-window generation keyed by session ID, interaction ID, document generation, item ID, and product ID while retaining the reported before quantity for delta validation and Undo provenance. A later cart observation can transition state only if all keys still match and it arrives before the monotonic-clock deadline. The page cannot arm a window by dispatching a synthetic DOM event because synthetic events have `isTrusted == false`; native code does not treat the page-reported URL or product ID as proof of origin.

A new interaction ID is created exactly once when ListRunner starts a selected-item interaction: when selection changes while the store is visible, `Show Store` presents a selected item, foreground recovery reactivates the selected item, or an explicit retry starts. The automatic search is a side effect within that interaction and does not create a second ID. Tapping the already-selected item does not create a new interaction or repeat the search. Returning to an item after selecting another creates a new interaction.

Native code increments the main-document generation on every committed main-frame navigation and every `WKWebView` rebuild. A ListRunner-initiated search operation is rebound to the resulting document generation when its intended navigation commits. Every other pending search, cart-confirmation, or stabilization operation belonging to the previous document is invalidated and changes its capability interaction outcome to `cancelled` without incrementing a failure count; an unrelated manual navigation therefore retains the selected item and interaction but cancels the automatic-search attempt. Automation injected into the new document receives the new native-issued generation. Messages and callbacks from an earlier document generation are ignored even when the host, session, interaction, and item still match.

Multiple Coles product results can report events for the same ListRunner item and interaction while retaining distinct store product IDs. Confirmed product associations and their latest quantities are retained in memory for that ListRunner item, including after a new interaction, web-view dismissal, or backgrounding. Associations for one item are cleared when that item is edited, merged, or deleted. All associations are cleared by `Clear List`, `Reset Coles Session`, or app termination and are not restored on relaunch; persisted ListRunner status remains, and later direct Coles interactions establish fresh associations. Quantity changes caused by cart restoration, page rendering, synchronization, or another source without an armed direct interaction update the observed quantity baseline but do not change ListRunner status.

Native code validates every message against the event-specific schema, active store configuration, actual native `WKWebView.url`, exact HTTPS host allowlist, main-frame source, isolated content world, active session, interaction and document generations when required, associated item, product correlation, and confirmation window before forwarding a transition to the shopping-run state engine. URLs reported by page JavaScript are diagnostic only and never establish trust. Delayed, duplicate, passive, forged, oversized, or otherwise stale messages are ignored and logged subject to diagnostic throttling. Bridge messages do not contain store credentials, payment details, or arbitrary page content.

Each undo record stores whether its confirmation originated from a confirmed Coles cart change or from a ListRunner-only action. Store-cart reversal is allowed only when that exact undo record originated from a confirmed cart change and contains the matching session ID, interaction ID, store product ID, before quantity, after quantity, and detected delta. Manual `Mark Added` creates a ListRunner-only undo record and never requests a Coles cart change. `Pause` preserves an existing Undo record and its provenance; it does not create or replace one or request a Coles cart change. `Undo` always restores the recorded ListRunner pre-action status regardless of the current associated Coles quantities. For an undo following a confirmed quantity increase, the strategy attempts to decrement exactly the detected quantity delta rather than remove the entire product, preserving any pre-existing quantity, but only when the current cart quantity still matches the recorded after quantity. A successful reversal updates the associated product quantity to the recorded before value without applying another status transition. If the cart changed again, or if any required correlation value or supported reversal strategy is unavailable, ListRunner still restores its own state, does not attempt product-specific cart reversal, and shows a non-blocking inline native banner reading `Could not undo store cart change` with an explicit close action on whichever ListRunner screen is visible. The banner is informational only and has no retry action. VoiceOver announces the banner, and the close control is labeled `Dismiss cart undo warning`. The banner remains until dismissed or the user navigates away, and is not persisted across relaunches.
Removal events without a valid active session, interaction, item, or correlated store product ID are ignored and do not change ListRunner item status. The Coles website remains the source of truth for the uncorrelated cart change.

Store configurations are data-only JSON files bundled with the app and decoded into typed Swift models using `Codable`. They may select only named detection strategies implemented by the generic bundled engine and cannot include executable JavaScript. Supported domains must use HTTPS and match an explicit host allowlist. Automated validation tests decode every bundled configuration and fail for unsupported schema versions, missing required fields, non-HTTPS domains, domains outside the host allowlist, or unsupported detection strategies. The engine and configurations are versioned and shipped with the app. Additional store configurations, remote configuration delivery, and arbitrary store-specific JavaScript hooks are later scope.

If the active store configuration unexpectedly fails to decode at runtime, ListRunner opens the store without injecting automation scripts and disables both session capabilities. Native overlay navigation and `Mark Added` remain available, the `Automation unavailable` badge explains the manual workflow, and the decoding error is logged locally. Configuration failure must not crash or block the shopping session.

### App metadata model
The app-level metadata record contains:
- Last active local calendar date
  - Optional until the first launch destination has been chosen.
  - Stored independently of the grocery list and used to choose same-day overlay restoration or later-day list/summary routing.
- Last saved local state revision
  - Required nonnegative 64-bit integer starting at zero.
  - Advances only with a successful transaction and seeds the next process's monotonic revision sequence.

### Core list model
The single active list contains:
- List ID
  - Required stable UUID generated by ListRunner.
- Items
  - Ordered relationship to the list's grocery items.
- Last overlay-selected item ID
  - Optional until the list first opens in the overlay.
  - References an item in the list and drives `Show Store` restoration.

### Core item model
For each grocery item, the following fields exist:
- Item ID
  - Required stable UUID generated by ListRunner.
  - Used for persistence, selection history, and deletion without relying on item text.
- List position
  - Required integer defining the item's order in the list and overlay carousel.
- Item name
  - Required
- Search term
  - Required
  - Derived from the item name and updated whenever the item name changes.
- Quantity amount
  - Optional numeric value; supports whole numbers and decimals.
  - Display guidance only; it does not control the Coles cart quantity.
- Quantity unit
  - Optional text or recognized unit such as `g`, `kg`, `L`, `cans`, or `packs`.
  - Display guidance only; it does not control the Coles cart quantity.
- Paprika reminder ID
  - Optional
  - Present only for items imported from Apple Reminders and used to synchronize completion and prevent duplicate imports.
- Selected Flag
  - Derived rather than persisted.
  - `Yes` when the item ID matches the list's last overlay-selected item ID and `No` for all other items.
  - Before the overlay has a recorded selection, the first item in list order is treated as `Yes`.
- Status
  - Required
  - New items default to `Pending`.
  - Enumerations
    - Skipped
    - Pending
    - Added

### Progression Rules
The selected card action and right-hand navigation control are determined by the following table when at least one `Pending` item remains:

| Selected item status | Card action | Right-hand control |
|---|---|---|
| `Pending` | `Mark Added` | `Skip` |
| `Added` | `Pause` during active automatic-add countdown; otherwise `Mark Pending` (except final confirmation) | `Next` |
| `Skipped` | `Mark Added` | `Next` |

When no `Pending` items remain, `All items handled` replaces the right-hand control regardless of the selected item's status, except while final-item confirmation temporarily shows `Undo` and `Finish`.

- The selected card displays the status label `Added` for an `Added` item and `Skipped` for a `Skipped` item. A `Pending` card does not display a `Pending` label; its pending state is conveyed by the available actions and surrounding context.

- Before an add starts cooldown, ListRunner temporarily records the item's current status for `Undo`. This pre-action status is transient and is discarded when cooldown ends or is cancelled. If another automatic add arrives during cooldown, the current `Added` status replaces the previous undo target so `Undo` applies to the latest add without returning the item to `Pending` or `Skipped`.
- Selecting `Mark Added` on a skipped item follows the same immediate-progression rule as any manual Mark Added, with Skipped recorded as its pre-action status.
- Manual `Mark Added` changes the item to Added and advances immediately to the next Pending item without countdown or paused confirmation, discarding its transient Undo record. If no Pending items remain, it retains the ListRunner-only Undo record for final-item Undo / Finish instead. It never requests store-cart reversal.
- Tapping `Pause` does not modify the Coles cart or item status. If a timed cooldown is active, immediately invalidate its timer generation and convert the current confirmation to untimed without changing the selected item or Undo record. If the confirmation is already untimed or the item is already paused, repeated taps are idempotent; they do not start a timer or replace the Undo record.
- Pause is available only during an active timed automatic-add confirmation. Revisiting an Added item offers Mark Pending without creating a paused state or Undo record. After pausing, replace Pause with Mark Pending and retain Undo / Next and the paused caption.
- Mark Pending changes the selected Added item to Pending, saves it, and keeps the item selected without changing the Coles page or cart. It cancels transient confirmation, clears Undo and pause state, updates totals, and replaces the card action with Mark Added. It is also available after Finish or when revisiting a completed run, reopening the run. During final-item confirmation, hide the card action and retain Undo / Finish; after Finish, Mark Pending becomes available. For imported Paprika items, the existing Pending-status reminder-uncheck rule applies. Mark Pending is not store-cart Undo and never requests removal or quantity changes.
- Manual pause is scoped to the current selected item, not the whole shopping run. It ends on `Undo`, `Next`, selecting another item (including Back), collapse, store dismissal, app backgrounding, session/list reset, item deletion/editing/merging, return to Pending after cart removal, or entry into a recovery panel. A positive-quantity decrease may discard the stale Undo record but does not by itself resume timing while the same item is manually paused. Pause is not persisted across app termination. When no Pending items remain, Pause has no effect and does not replace `All items handled`. `Pause` is not shown during final-item confirmation.
- When an automatic add or manual `Mark Added` handles the final `Pending` item, no timer starts. ListRunner records the pre-action status and provenance, enters final-item confirmation, keeps that item selected, and shows persistent `Undo` and `Finish`. `Finish` discards the Undo record and reveals `All items handled` without changing the Coles cart or item status.
- `Undo` during final-item confirmation restores the recorded pre-action status and ends confirmation. Confirmed-cart provenance uses the same best-effort store reversal rule as cooldown Undo; ListRunner-only provenance never requests a Coles change. The normal pending-item controls return after restoration.
- Collapse, top-handle dismissal, and app backgrounding preserve final-item confirmation and its Undo record. If the app terminates, resets the Coles session, clears the list, or deletes the confirmed item, confirmation ends and its transient record is discarded; termination leaves the item's persisted `Added` status accepted as completion.
- Later confirmed cart increases or positive-quantity decreases during final-item confirmation update product associations but do not replace the original final-item Undo target. A confirmed removal that reduces every associated product to zero restores the item to `Pending` and ends final-item confirmation. If later cart activity means the current store quantity no longer matches the Undo record's after quantity, final `Undo` still restores ListRunner state but follows the existing store-reversal failure path.
- `Undo` during timed or untimed confirmation ends that confirmation, clears manual pause, and restores the recorded pre-action status. Undoing the first add therefore restores `Pending` or `Skipped`; pausing that confirmation does not change what Undo restores. Reversing the store cart change remains best-effort.
- Selecting another item during cooldown cancels the timer without changing the previous item's `Added` status, then selects and searches the chosen item.
- Pulling down from the native top drag handle during cooldown cancels the timer, keeps the current item in `Added` status, invalidates the active interaction ID, and ignores delayed bridge messages for that interaction.
- Pulling down on the overlay during cooldown collapses it, cancels the timer, discards the undo target, and keeps the current item in `Added` status without invalidating the interaction. A later confirmed add while collapsed expands the overlay and creates a new undo target for that confirmed change.
- When cooldown completes or the user skips the cooldown with `Next`, ListRunner advances to the next item with `Pending` status. Items that are already `Added` or `Skipped` are passed over.
- Automatic advancement caused by cooldown completion, `Next`, or `Skip` is added to selection history. `Back` therefore returns to the item that was selected immediately before the automatic advancement.
- `Skip` is used when an item is unavailable at the store or not applicable to the current shopping run. Skipping changes the item status to `Skipped`. If another `Pending` item remains, ListRunner advances to it immediately. If the skipped item was the final pending item, it remains selected and `All items handled` appears immediately. Skipped items are not automatically revisited at the end of the run.
- `Back` only moves focus to the last selected item. It does not change the status of the current item or the destination item. This is based on selection history rather than list order, because users can tap item cards several items backward or forward.
- `Back` removes the destination entry from selection history and does not add the item being left back into history. Repeated taps therefore continue walking backward instead of alternating between two items.
- Tapping the already-selected item does not add a duplicate entry to selection history.
- Selecting a different item by tapping a card or list row pushes the previously selected item ID onto selection history before changing selection. This also applies when card selection cancels an active cooldown.
- Tapping an item card makes that item the current focus and immediately searches for it on Coles when search automation is available; otherwise it leaves the Coles page unchanged for manual searching.
- Tapping an item on the list/summary screen follows the same selection and search behavior as tapping an item card, then opens the overlay. Selection alone does not change item status.
- Completion is derived from item statuses rather than represented by a separate persisted state. Final-item confirmation is a transient recovery state layered over a status-complete list; after it ends without restoring a `Pending` item, the overlay displays `All items handled` in place of `Skip`/`Next` while keeping item navigation available.
